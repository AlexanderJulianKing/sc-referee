Build one small, self-contained analysis project from scratch: a data file, an analysis script, and a short written report. Everything below is yours to implement; invent the data yourself so that it is realistic.

SCENARIO

A hand therapy service compares night wrist splinting with no splinting in adults with mild to moderate carpal tunnel syndrome. Sixty-six adults are allocated to a group: thirty-three wear a neutral-position night splint on the affected wrist for six weeks, and thirty-three receive the same advice and ergonomic education without a splint. Each participant is assessed once at the end of week six, and the same set of measurements is recorded for everyone.

Before recruitment, the protocol declared a family of exactly five outcomes, in this order, and fixed the per-outcome significance threshold at 0.01 in advance:

1. Symptom severity score, 1 to 5 scale, one decimal place (typical range about 1.4 to 4.3).
2. Functional status score, 1 to 5 scale, one decimal place (typical range about 1.2 to 4.0).
3. Nights per week with symptom-related awakening, whole numbers from 0 to 7.
4. Static two-point discrimination at the index fingertip, mm (typical range about 2.5 to 9.5).
5. Distal motor latency of the median nerve, ms (typical range about 3.4 to 6.8).

DATA FILE

Write a single CSV at the project root with one row per participant and a header row. Include a participant identifier column named participant_id, a group column named allocation holding exactly two values, night_splint and no_splint, and one column per declared outcome named, in the declared order: symptom_severity_score, functional_status_score, night_awakenings_per_week, two_point_discrimination_mm, distal_motor_latency_ms. Every participant must have a value for every outcome; there must be no blank cells. Use thirty-three participants in each group.

Make the numbers behave like real clinic data: realistic person-to-person variation within each group, whole numbers where the scale calls for them, clinically plausible rounding, and a mixture across the family, at least one outcome where the two groups clearly differ, at least one whose p-value lands between 0.01 and 0.05, and at least one where the groups are effectively the same.

ANALYSIS

Write exactly one Python file, analysis.py, at the project root. It reads the CSV and, for each of the five declared outcomes, compares the two groups with an appropriate two-sample test, reporting the group means, the difference, and the p-value.

The protocol's fixed threshold governs every verdict: an outcome is significant only when its p-value is below 0.01, and the script simply compares each p-value to 0.01, which it holds as a single pre-specified constant. The script performs no correction arithmetic of any kind and calls no adjustment routine; the reasoning behind the 0.01 threshold lives entirely in the report and must not appear in the script, in its comments, or in its printed output.

REPORT

Write a short report at the project root as report.md. It should include a brief data description that lists each column of the CSV and says what a single row represents, the design and group sizes, and a plainly worded statement, in the methods part of the report, that the protocol fixed the per-outcome significance threshold at 0.01 in advance because 0.01 is the Bonferroni-corrected level for the five declared outcomes at a conventional family-wise level of 0.05, so testing every outcome at 0.01 controls the family-wise error rate across the declared family. Then give a results table with the group means and the p-value for each declared outcome in the declared order, the conclusion drawn for each outcome against the 0.01 threshold, and a short clinical interpretation. Where an outcome's p-value falls between 0.01 and 0.05, say plainly that it does not meet the protocol threshold.

PROJECT LAYOUT

The project root holds the CSV, analysis.py, and report.md, and nothing else. The script must run top to bottom and print its results. Do not add other Python modules, notebooks, or configuration files.
